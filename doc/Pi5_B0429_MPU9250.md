# Live mono VIO on Raspberry Pi 5 with Arducam B0429 and MPU-9250

`granite_pi_cam_imu_vio` reads an Arducam B0429 (onsemi AR0234 color global shutter, 2-lane CSI-2) on a Raspberry Pi 5 camera port and an MPU-6500/9250 IMU on an I2C adapter, for example a CP2112 USB-to-SMBus bridge. It runs Granite mono VIO or mono VO. It can also record an EuRoC dataset for calibration.

The tested system is a Raspberry Pi 5 (8 GB) with Ubuntu 24.04 and kernel `6.8.0-1064-raspi`. The camera is on CAM/DISP 1. The IMU is an MPU-9250 (`WHO_AM_I` 0x71) at address 0x68 behind a CP2112 (`/dev/i2c-15`).

## Camera driver

The B0429 has an Arducam bridge MCU at I2C address 0x0c. It does not use a raw AR0234 sensor driver. The in-kernel `arducam-pivariety` driver supports it. Set this in `/boot/firmware/config.txt` and reboot:

```ini
camera_auto_detect=0

[all]
dtoverlay=arducam-pivariety
```

Use `dtoverlay=arducam-pivariety,cam0` for CAM/DISP 0. After the reboot, `dmesg` shows `arducam-pivariety 11-000c: firmware version: ...`. The sensor offers SGRBG10 at 1920x1200, 1920x1080 and 1280x720.

The example does not use libcamera. The Ubuntu libcamera 0.2 package has no Pi 5 PiSP support for this sensor. The example configures the rp1-cfe media graph itself and reads packed RAW10 from `rp1-cfe-csi2_ch0`. It converts the Bayer image to grayscale and runs its own automatic exposure.

## Device access

The user needs the `video` group for the camera and access to the I2C device for the IMU:

```sh
sudo groupadd --system i2c
echo 'KERNEL=="i2c-[0-9]*", GROUP="i2c", MODE="0660"' | sudo tee /etc/udev/rules.d/60-granite-i2c.rules
sudo usermod -aG i2c,video $USER
```

Log in again after the group change.

## Build

```sh
sudo apt-get install -y gcc g++ cmake git ninja-build libtbb-dev libeigen3-dev \
  libglew-dev ccache libjpeg-dev libpng-dev liblz4-dev libbz2-dev \
  libboost-regex-dev libboost-filesystem-dev libboost-date-time-dev \
  libboost-program-options-dev libgtest-dev libopencv-dev v4l-utils i2c-tools
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DUSE_OPENMP=OFF
cmake --build build -j3 --target granite_pi_cam_imu_vio test_pi_sensor_utils
./build/test/test_pi_sensor_utils
```

`GRANITE_BUILD_PI_CAMERA` is on by default on Linux. Three compiler jobs fit in 8 GB. A full build (`cmake --build build -j3`) takes about one hour on the Pi 5. With gcc 13 (Ubuntu 24.04), the build disables `-Werror` for three warning classes that come from Eigen, TBB, Pangolin and the granite-headers tests.

## Run

```sh
# Image and IMU delivery only
./build/granite_pi_cam_imu_vio --capture-only --duration 10
# Record an EuRoC dataset for calibration
./build/granite_pi_cam_imu_vio --record ~/pi-calib --duration 60
# Mono VIO with a calibration at 1280x720
./build/granite_pi_cam_imu_vio --calib calib.json --resize-half --trajectory /tmp/vio.csv
# Mono VO
./build/granite_pi_cam_imu_vio --calib calib.json --resize-half --use-imu 0
```

The default sensor mode is 1280x720 at 30 fps. `--width` and `--height` select another mode. `--resize-half` averages each 2x2 Bayer quad into one gray pixel and scales the intrinsics. The calibration file always uses the capture resolution. The live window opens only when `DISPLAY` is set. `--no-gui` disables it. Use `--help` for all options.

`--exposure 0` (default) enables automatic exposure. It uses exposure first, up to `--max-exposure` (8 ms), and analogue gain after that, up to `--max-gain`. A positive `--exposure` sets a manual exposure in milliseconds with `--gain` in dB (0 to 11 dB). A short manual exposure decreases the motion blur. The exposure cannot be longer than the frame period minus 0.1 ms; the example uses the limit and prints a warning.

The sensor mode limits the frame rate. The example sets the vertical blanking for `--fps` and prints the frame rate that the sensor uses. If the mode cannot give the requested rate, it prints a warning.

`data/uvify_config_mono_vio.json` is a VioConfig for the Pi. Its `camera.fps`, `camera.exposure_ms`, `camera.gain_db` and `camera.resize_half` keys set the camera. These keys are optional, and a command line option has priority over its key. The file sets 60 fps, a 3 ms exposure, 6 dB gain and half resolution. At 60 fps with the live window over SSH X forwarding, full resolution lost 11-18% of the frames at the optical flow input, and half resolution lost none (stationary camera, 15 s). `vio_take_keyframe_iteration` must be less than `vio_max_iterations`:

```sh
./build/granite_pi_cam_imu_vio --calib calib.json --config-path data/uvify_config_mono_vio.json
```

The analogue gain in dB uses the gain fit of the xeye B0429 node (driver value 100 + 382 x (linear gain - 1)), which was measured with the Jetson driver. The fit was not measured on the Pi.

## Calibration

`data/pi5_b0429_mpu9250_calib_uncalibrated.json` is a placeholder. It has guessed intrinsics, an identity camera-to-IMU transform and approximate MPU-9250 noise values. Its gyroscope bias is the stationary mean of the tested unit, (0.0806, -0.1030, -0.0121) rad/s; the bias of another unit is different. It lets the pipeline run, but the estimate is not metric or accurate with it. Calibrate the system before use:

1. Record a dataset of an AprilGrid with slow motion, for example `--record ~/pi-calib --duration 60`.
2. Run `granite_calibrate --dataset-path ~/pi-calib --dataset-type euroc --aprilgrid data/aprilgrid_6x6.json --result-path ~/pi-calib-result --cam-types kb4`.
3. Record a second dataset with motion on all axes.
4. Run `granite_calibrate_imu` on the second dataset with the result path of step 2.

See [Calibration](Calibration.md) for the tool options.

## Test results

Measured on 2026-10-23 with the system stationary in a dark room:

| Check | Result |
|---|---|
| Camera, 1280x720 at 30 fps | 30.18 fps, frame interval 33.14 ms ± 0.01 ms, no sensor drops |
| IMU, 200 Hz FIFO | 200.07 Hz, sample interval 4.90–5.02 ms, no FIFO overflow |
| Stationary accelerometer norm | 9.84 m/s² |
| `--capture-only`, 15 s | 453 images, 2998 IMU samples, monotonic times |
| Mono VO, 10 s, `--resize-half` | 301 states at 30.9 Hz, tracking |
| Mono VIO, 20 s, `--resize-half` | Runs; no states, because metric initialization needs motion |
| Mono VIO, 10 s, 1280x720 | Runs at 30.9 input fps; no states for the same reason |
| `--record`, 5 s | EuRoC layout with 150 images and 992 IMU samples |
| `test_pi_sensor_utils` | 6 of 6 pass on x86 and on the Pi |
| Full `ctest` on the Pi | 171 of 172 pass; see below |

`MonoVioRobustness.SmallTranslationParallaxDoesNotTriggerRotationRecovery` fails on the Pi 5 (aarch64) every time: one finite landmark instead of zero, and x = 0.901 instead of 0.782 ± 0.04. It passes on x86. This example does not change the estimator; the cause is not known.

The scene was too dark for feature tracking (mean brightness at the black level with 8 ms and 8x gain). Metric VIO, tracking accuracy and the calibration were not tested.

## IMU timing

The MPU runs at 200 Hz with its FIFO enabled. The example reads the FIFO every 20 ms. A CP2112 transfer takes at least 5 ms, and reads of 256 bytes or more fail. Direct register polling is limited to about 140 Hz, and FIFO reads reach about 6.6 KB/s. Rates above 400 Hz do not fit.

The FIFO has no timestamps. The example assigns each sample a time from its index. Each FIFO count read gives an upper bound (end of the read) and a lower bound (start of the read minus one period) for the newest sample. The clock uses the center of the tightest bounds in a 0.5 s window. The period comes from the slope of the bounds over a long baseline. In a simulation with a 1% oscillator error, the error stays below 2 ms.

rp1-cfe stamps each buffer at the end of frame (`V4L2_BUF_FLAG_TSTAMP_SRC_EOF`). With a global shutter, the readout of all rows follows the exposure. The image time is the end of frame minus the readout time (rows x line time) and half the exposure. The example adds `cam_time_offset_ns` of the calibration file to the image time, because the estimators do not apply it. The first three frames after stream start are discarded; they use the default frame length.

A direct connection to the Pi 5 GPIO I2C or SPI with the INT pin gives per-sample timestamps from the kernel `inv-mpu6050` IIO driver (`dtoverlay=i2c-sensor,mpu9250,int_pin=<gpio>`). The example does not support that path yet. See [MPU-9250 direct wiring](Pi5_MPU9250_Wiring.md) (Korean) for the pin map and the SPI overlay.
