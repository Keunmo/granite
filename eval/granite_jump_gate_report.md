# Granite 단안 VIO 한 프레임 위치 튐: 원인과 gauge 게이트

대상: `mono-vio-merged`, Cam1, inertial 초기화, Unreal city 시퀀스(6118 프레임, 경로 약 2.4 km).
설정: grid 25 = `eval/config/oi_g25_det.json`, grid 40 = `eval/config/oi_g40_det.json`.
게이트 켬 설정: `eval/config/oi_g25_det_gauge_gate.json`, `eval/config/oi_g40_det_gauge_gate.json`.
모든 실행은 데스크톱에서 `--num-threads 4`로 합니다.

## 1. 결론

- 튐은 슬라이딩 창 전체가 같은 병진으로 한 번에 움직여서 생깁니다. 이 방향(공통 병진)은 관측되지 않습니다.
- 공통 병진을 붙잡는 것은 주변화 prior의 약한 위치 정보뿐입니다. 그런데 이 정보는 다른 상태와 강하게 결합되어 있습니다.
- LM λ가 1e-10 이하로 내려가면 이 방향의 감쇠가 사실상 없습니다. 그러면 다른 상태의 작은 변화가 미터 단위의 창 이동으로 커집니다. 비용은 거의 바뀌지 않으므로 LM이 그 단계를 수락합니다.
- 게이트(`vio_gauge_gate`)는 LM 단계를 풀 때 공통 병진 방향에만 정보 w를 더해 다시 풉니다. 목적 함수와 prior는 바꾸지 않습니다. 출력 포즈를 거르지 않습니다.
- 게이트 켬: 전체 구간 grid 25, grid 40 모두 C4 튐 0회입니다. 기존 기준과 새 기준(C2b, C3b)에서 모두 PASS입니다. ATE는 grid 25에서 같고(3.01 → 3.00 m), grid 40에서 줄어듭니다(4.74 → 3.74 m).
- 게이트 끔: 결과가 HEAD와 바이트 단위로 같습니다(md5, 1000 프레임과 전체 구간, grid 25와 grid 40).

## 2. 원인

### 2.1 진단 방법

`eval/experiments/jump_diag_gauge_trials.patch`(임시 패치, 커밋한 코드에는 없음)로 프레임마다 아래를 기록했습니다.

- IMU 예측 상태와 최적화 후 상태의 차이, 직전 상태의 보정량(prev_corr), 키프레임 포즈의 보정량(최소, 최대)
- 반복 횟수, 시도 횟수, 거절 횟수, 마지막 λ, 비용(vision, IMU, prior, bias)의 최적화 전후 값
- 이상치 필터와 `updateMonoLandmarks`가 지운 관측 수, 새 랜드마크 수, 키프레임 추가, 주변화된 키프레임 수
- IMU 예측 대비 Mahalanobis 거리: 최적화 전 상태에서 prior + IMU 항만의 Hessian으로 계산한 보정량의 m²
- 지정한 시간 구간에서 반복마다: 전체 H의 작은 고유값 6개, b와 증분의 고유벡터 성분, 항별 공통 병진 기울기(Nᵀb)와 |H N|

- g25 233.03 s, g40 382.53 s도 같습니다. 증분의 95 % 이상이 작은 고유값 3개 방향에 있습니다.
- λ는 수락될 때마다 1/3이 되고 거절될 때만 커집니다. 전체 구간에서 프레임 절반의 마지막 λ가 8.4e-7(g40)과 4.5e-23(g25) 이하입니다. 같은 현상은 앞 1000 프레임에서 작습니다(게이트 켬 기록: 감쇠 전 공통 병진 최대 0.024 m). 전체 구간에서는 3–7.6 m까지 커집니다.

### 2.4 확인하지 못한 것

- g40 210.60 s와 346.45 s는 새 키프레임 프레임입니다. 여기서는 증분에 공통 병진(약 3.1)과 함께 창의 변형(0.7)이 있습니다. 오래된 키프레임 2개는 0.09 m, 나머지는 1.6 m 움직입니다. vision 비용이 크게 줄어듭니다(392 → 292). 게이트는 이 튐도 없앱니다. 그러나 변형 부분의 원인(새 랜드마크의 깊이, 잘못된 대응 등)은 확인하지 못했습니다.
- 정지 직전(377–385 s)의 튐도 공통 병진 이동입니다. 그러나 이 구간의 5 s 창 오차는 게이트 후에도 일부 설정에서 남습니다(5절). zero-velocity 계열 문제인지 확인하지 못했습니다.

## 4. 게이트 설계

설정(모두 `optional_nvp`, 기존 설정 파일은 그대로 읽힘):

| 항목 | 기본값 | 뜻 |
|---|---|---|
| `config.vio_gauge_gate` | false | 게이트 켬/끔 |
| `config.vio_gauge_gate_m` | 0.0 | LM 단계의 공통 병진이 이 값 [m]보다 크면 다시 풂. 0이면 모든 단계 |
| `config.vio_gauge_gate_weight` | 50 | 공통 병진 방향(정규 직교 기저)에 더하는 정보 |

동작(`KeypointVioEstimator::gateGaugeStep`, `src/vi_estimator/keypoint_vio_mono.cpp`):

1. LM의 각 시도에서 원래대로 `(H + diag) inc = b`를 풉니다.
2. 공통 병진 u = 모든 포즈와 상태의 병진 증분의 평균을 구합니다.
3. |u| > `vio_gauge_gate_m`이면 `(H + diag + (w/n) N Nᵀ) inc = b`를 다시 풉니다. N은 모든 변수의 병진 블록에 단위 행렬을 둔 3열 행렬, n은 변수 수입니다.
4. H, b, prior, 비용 계산, 수락 판정은 바꾸지 않습니다.

설계 근거:

- 공통 병진은 관측되지 않는 방향입니다. 이 방향의 이동은 비용을 바꾸지 않으므로 LM의 수락 판정이 막지 못합니다. 따라서 풀이 단계에서 막습니다.
- 증분에서 공통 병진을 빼기만 하면 다른 변수의 해가 공통 병진의 이동을 전제한 채로 남습니다. 이 방법은 발산했습니다. 다시 풀면 다른 변수가 제한된 공통 병진에 맞는 해를 얻습니다.
- prior의 공통 병진 정보는 지우지 않습니다. 지우면 ATE가 나빠졌습니다(3절).
- 임계값을 두면 임계 아래의 작은 이동이 여러 반복에 걸쳐 쌓여 튐이 남았습니다. 따라서 기본값은 0(모든 단계)입니다. 이름은 요청에 맞춰 gate로 둡니다.
- 로그: 1000번 적용마다 `VIO_GAUGE_GATE count=… above_0.1m=… max_common_m=…`를 출력합니다. above_0.1m은 감쇠 전 공통 병진이 0.1 m를 넘은 단계 수입니다.

## 5. 판정

기호: P = 통과, F = 실패. C2b, C3b는 `eval_pose.py --abs-window`로 추가한 새 기준입니다.

- C2b: 5 s 창마다 |d_est − d_gt| ≤ max(0.10 d_gt, 0.5 m). 창 간격 2.5 s, 최소 이동 조건 없음.
- C3b: 이웃 창의 오차 e = d_est − d_gt의 변화 |e_i − e_(i−1)| ≤ max(0.10 × 두 창 GT 이동의 평균, 0.5 m).
- 두 기준 모두 첫 포즈 후 10 s부터의 창을 씁니다. "판정(새)"은 C2, C3 대신 C2b, C3b를 쓴 판정입니다. 기존 출력과 기존 판정은 바뀌지 않습니다.
