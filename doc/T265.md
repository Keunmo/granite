# Live T265 odometry on Raspberry Pi 4

The examples use the T265 fisheye images and raw accelerometer/gyroscope streams. They estimate poses in Granite; they do not use the T265 firmware pose stream.

## Build

Install the normal Granite dependencies and librealsense2 (tested with 2.53.1). Initialize the repository submodules before building. `GRANITE_BUILD_GUI=OFF` omits Pangolin and its GUI applications. The T265 runners provide a lightweight OpenCV GUI independently of this build flag; use `--no-gui` for headless execution. On RPi4 use one compiler job to limit peak memory:

```sh
cmake -S . -B build-rpi4 \
  -DCMAKE_BUILD_TYPE=Release \
  -DGRANITE_BUILD_GUI=OFF \
  -DGRANITE_BUILD_REALSENSE=ON \
  -DUSE_OPENMP=OFF
cmake --build build-rpi4 --target granite_rs_t265_mono_vo \
  granite_rs_t265_mono_vio granite_rs_t265_vo granite_rs_t265_vio -j1
```

## Four modes

```sh
# Left fisheye, original Granite monocular VO
./build-rpi4/granite_rs_t265_mono_vo --resize-half
# Left fisheye, monocular metric VIO
./build-rpi4/granite_rs_t265_mono_vio --resize-half
# Both fisheyes, stereo VO
./build-rpi4/granite_rs_t265_vo --resize-half
# Both fisheyes, stereo VIO
./build-rpi4/granite_rs_t265_vio --resize-half
```

`--mono-camera 2` selects the right fisheye for either monocular example. `--mono-camera 0` selects stereo. The general runner also accepts `--use-imu true` or `--use-imu false`.

`--resize-half` downsamples 848 × 800 images to 424 × 400 using area averaging. It scales focal lengths by 0.5 and transforms principal points as `(c + 0.5) * 0.5 - 0.5`, matching the pixel centers used by the resampling. Fisheye distortion and camera-to-IMU extrinsics remain valid. Without the flag, native resolution is used.

## Monocular VIO initialization

Monocular VO supplies the visual bootstrap, retaining Granite's existing keyframe selection, infinity landmarks and scale robustness behavior. A separate visual-inertial alignment estimates metric scale, gravity direction, velocity and gyroscope bias from the visual trajectory and IMU preintegration. The transferred map is rescaled and passed to the existing inertial optimization backend.

Metric initialization needs translation with changing acceleration and sufficient visual parallax. Move the camera through a short smooth motion; a stationary camera, pure rotation or constant velocity cannot determine scale. After metric initialization, the single-camera backend retains infinity bearings during pure rotation and preserves the existing metric state, velocity, gravity, bias and marginalization prior when finite points disappear. Infinity observations constrain rotation without the VO zero-translation regularizer. The same tracked bearings can be promoted to finite metric depth when translation provides sufficient rotation-compensated parallax and validated baseline. Wrong associations are rejected before optimization; rejected continuous track IDs are not silently recreated when their old host is marginalized. Pyramid-level weights, configured inverse-distance limits and robust residual filtering are retained.

Keyframe selection combines coverage loss with conditional visual information after landmark elimination. Bearing-only tracking uses rotation information; IMU information does not conceal lost visual coverage. This adapts the VO information-selection idea; it is not the VO pose-only marginal entropy or arbitrary-scale reinitialization algorithm.

`VioStateData.mono_vio_support` reports `METRIC` with at least five currently connected finite points, `BEARING_ONLY` with at least five infinity bearings, and `INERTIAL_ONLY` otherwise. These are support indicators, not covariance estimates or proof of instantaneous scale observability. Old inactive finite points do not count toward current support. During inertial-only output, pose propagation continues but position/velocity can drift. When retained metric landmarks disagree with inertial pose prediction, a RANSAC PnP recovery is attempted using unprojected camera bearings and the existing metric 3D map. At least 20 matches and 70% support must pass the actual camera-model reprojection check. Pose innovation limits grow with the visual outage duration; velocity, bias and metric gauge are preserved. Empty frames do not create new keyframes that would evict the recovery map. This is local metric reacquisition, not global relocalization. When only retained infinity bearings remain after an actual image gap, majority-validated rotation RANSAC can recover orientation while preserving metric translation, velocity and bias. This requires 20 matches, 80% support and bounded angular innovation, and does not run for continuous images with translation parallax. A majority-supported positive-depth translation hypothesis vetoes rotation recovery even below the normal triangulation baseline, protecting nearby planes moving during image gaps. Bearings remain at infinity while their infinity model still explains the current image. Rotation recovery is conservative: if gyro drift also admits the finite-parallax hypothesis, it can refuse recovery. The synthetic yaw-drift cases do not establish recovery for every bias axis or scene. Large inertial errors, lost maps or long visual outages still require further validation.

Until initialization succeeds the example reports `metric_initialized=false` and emits no metric poses. The state output starts when the alignment succeeds. Gravity is aligned to the estimator world frame; world position and yaw remain arbitrary. Mono VO retains its arbitrary scale.

The alignment was independently implemented using Granite preintegration and the standard visual-inertial alignment equations. The [VINS-Mono initialization implementation](https://github.com/HKUST-Aerial-Robotics/VINS-Mono/blob/master/vins_estimator/src/initial/initial_aligment.cpp) was consulted as an algorithm reference; its source was not copied.

## Capture, logging and performance

```sh
./build-rpi4/granite_rs_t265_mono_vio --resize-half --no-gui --duration 30 \
  --num-threads 3 --trajectory /tmp/mono-vio.csv --save-calib /tmp/t265.json
./build-rpi4/granite_rs_t265_vio --resize-half --no-gui --capture-only --duration 10
```

Each startup resets the selected T265 and waits five seconds for USB re-enumeration, matching the original device example. This reboot is excluded from the processing timer. GUI is enabled by default (`--no-gui=false`). `--no-gui` disables display initialization and visualization output. See [GUI controls and display requirements](T265_GUI.md). Use `--help` for all options. `--duration 0` runs until Ctrl-C. `--exposure 0` enables automatic exposure; positive values set manual exposure in milliseconds (the tested T265 reports 0.2–16 ms). Exposure mode and the initial value are configured before streaming, and values outside the SDK range are rejected. `--config-path` loads a Granite JSON configuration after the example defaults. The example defaults enable realtime processing, five keyframes and four optimizer iterations.

Image capture has a bounded queue and may drop stale frames when processing falls behind. IMU samples are retained. Per-second statistics report received image rate, output state rate, image drops, IMU queue depth and newest captured image timestamp minus output timestamp in milliseconds (`lag_ms`). This lag measures backlog relative to the current stream, not physical sensor latency. The SDK can emit a frameset with a new left image and the preceding right image; stereo accepts matched frame numbers only. Every mode rejects duplicate or decreasing selected-image timestamps. `raw_images`, `pair_rejects` and `time_rejects` expose this filtering. `--skip-frames N` intentionally processes every Nth image and is separate from half resolution.

Trajectory CSV contains timestamp, position, quaternion and velocity. If accepted images stop arriving for three seconds after startup, the example reports a stalled stream and exits with failure. Shutdown cancels bounded flow queues and releases IMU waits, including when a stream stops while the backend waits for IMU.

Stationary mono VIO capture can exit successfully with zero states while awaiting observable motion; that is not evidence of successful metric initialization.

## Tests

`test_t265_image` verifies downsampling, image stride, monocular camera selection and calibration projection. `test_mono_vio_alignment` verifies metric scale, gravity, gyroscope bias, camera/IMU lever arm and unobservable-input rejection. `test_mono_vio` drives the estimator with synthetic temporal image observations and IMU, checking metric motion, finite landmarks, stationary initialization deferral, initial accelerometer bias and a small backend keyframe window.

## RPi4 validation (2026-10-02)

Test hardware: Raspberry Pi 4, Ubuntu 22.04 aarch64, T265 firmware 0.2.0.951 over USB 3.1, librealsense 2.53.1; three processing threads. Native regression suite: 141/141 passed. ARM image, mono inertial alignment/estimator and shutdown tests: 14/14 passed. Exported device calibration was checked at full/half resolution for stereo and both mono cameras.

The camera was stationary and its images were nearly uniform and dark (mean 19.7/255, standard deviation 1.4). These measurements establish streaming and processing throughput in this scene; textured moving-scene speed and trajectory accuracy remain unverified. Mono VIO correctly deferred metric initialization with this unobservable input. Its metric scale, gravity, bias and motion were verified with synthetic image observations and IMU on both x86 and ARM.

## USB outages and mono initialization diagnostics

A USB `RS2_USB_STATUS_IO` followed by `Stream transfer failed` means the raw transport stopped. In the 2026-10-03 desktop report, kernel logs also showed the camera disappearing and reappearing as `03e7:2150` Movidius boot firmware before returning as `8087:0b37` T265. The camera was attached through a USB3 hub. This identifies a device/USB outage, but does not distinguish firmware crash from cable/hub/power failure. Test a direct host USB3 port with a short reliable cable. Half resolution resizes images on the host; it does not reduce T265 USB traffic. Startup `NO_DEVICE` messages during the explicit hardware reset can occur before successful streaming and are distinct from a runtime outage.

The runners now cleanly stop all SDK/flow/estimator work after a stream watchdog failure and retry a fresh session up to three times, waiting five seconds between attempts. `--reconnect-attempts 0` restores immediate failure on a stream outage. An exhausted retry budget exits with failure; an invalid state, GUI failure or ordinary configuration error is not retried. Ctrl-C interrupts the reconnect wait. `--duration` covers processing and reconnect time from the first session's start, rather than restarting its timer after each outage. The synchronous SDK startup/hardware reset can still delay a stop request; this is not a hard wall-clock deadline.

Each reconnect creates a new estimator and initializes metric scale again; missing IMU samples cannot justify a continuous trajectory through the outage. The first trajectory uses the requested path, and later sessions use `<path>.segment-1.csv`, `<path>.segment-2.csv`, etc. Each contains its own coordinate origin. The GUI trajectory also restarts. This is outage recovery, not a repair of an unstable physical USB connection.

The mono crash from the same report was independently localized by matching the exact kernel instruction address to `LandmarkDatabase::removeKeyframes` in the original binary. A newly created landmark with no accepted observations lacked a count entry. Birth now initializes count zero and an empty host observation map, so later query, removal and marginalization are valid. The regression previously exited with SIGSEGV and now passes.

Scale itself depends on the arbitrary visual map units: a scale of 2803.86 can be valid if the visual trajectory is correspondingly small. The initializer propagates preintegration position/velocity covariance through the actual unweighted least-squares sensitivity and rejects relative scale standard deviation above 0.1. This conditional uncertainty holds visual poses and the shared estimated bias fixed; it does not model their full uncertainty and is not a complete initialization guarantee.

Native regression verification for this repair: 166 tests passed, including the zero-observation crash, noisy low-excitation scale rejection, high-scale observable positive control and bounded reconnect policy and throwing SDK-stop cleanup tests. Actual camera reconnect/long-run verification is still outstanding because the active execution environment denies USB netlink access. The user's raw log and local kernel journal establish the original outage and crash; synthetic tests establish the repaired software paths.
